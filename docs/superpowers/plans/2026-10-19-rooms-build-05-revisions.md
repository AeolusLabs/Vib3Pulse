## B. Security design (the review checklist; every item needs a test file case)

1. **Eligibility is one function, used twice.** `sprayEligibility` (shared, pure) is called by the server endpoint with data loaded from the database (never from the request) and mirrored by the client for UI. Payer: `isIdVerifiedAdult`, not the recipient, signed in, account not banned. Room: `moneyEligibleRoom` (18+/21+, not minors' room), status live (not scheduled, not ended), payer currently a member of the room in the hub (a socket in the room), payer not banned/kicked from it. Host: `isIdVerifiedAdult` with a verified payout account (same check phase 4 uses for `canSellTickets`). Recipient: the host, OR a member currently ON STAGE (co-host or guest speaker) who is `isIdVerifiedAdult` with a verified payout/subaccount. Check at start AND again inside `finalizeSpray` (they may have left, lost stage, been kicked, been banned, been un-verified, the room may have ended).
2. **No oracle.** Every eligibility failure for payer, room or recipient state answers the SAME `403 { code: "SPRAY_UNAVAILABLE", message: "Spraying is not available here." }`, same shape and no recipient/room detail, whether the caller is a teen, unverified, outside the room, spraying a non-stage person, a person without payout account, or the flag is off. Only genuinely payer-owned facts get specific codes: `401` signed out, `400 BAD_REQUEST` malformed body, `409 ROOM_LIMIT` / `409 DAILY_LIMIT` (their own limits), `409 IDEMPOTENCY_MISMATCH`, `429 RATE_LIMITED` with `Retry-After`, `402 PAYMENT_DECLINED` (their card). Do the cheap auth/eligibility checks BEFORE any provider call or database write.
3. **Idempotency.** Client UUID `idempotencyKey` (validated as UUID v4 shape). Unique index on `(payer_id, idempotency_key)` (NOT global, so one user can never squat or probe another's key). A request hash `sha256(roomId|tier|targetId)` is stored; a replay with the same key but different hash is `409 IDEMPOTENCY_MISMATCH` and never charges. A replay with the same hash returns the first result (status read from the row) and never starts a second charge. Insert the row with `ON CONFLICT DO NOTHING` then re-read; never read-then-insert.
4. **Reference.** Server generated, `vib3rs_<24 hex nonce>_<32 hex HMAC>`, the HMAC binds `(roomId, payerId, tier, recipientId)` (copy `server/rooms/ticketReference.ts`, domain-separated string `room-spray:v1:`, same secret rule, fail closed when no secret). `provider_ref` unique. Webhook and verify accept a spray only if the reference passes the MAC check against the stored row's room/payer/tier/recipient, the stored `amount_kobo` equals the provider-verified amount exactly, and the currency is NGN. A transaction someone made themselves can never become a spray. A webhook for a reference with no row, or a bad MAC, answers 200 and does nothing (log reference prefix only).
5. **Limits are atomic and reserve-first.** `addSpend(roomId, userId, kobo, limitKobo)` is one conditional upsert (`INSERT ... ON CONFLICT DO UPDATE SET spent = spent + $kobo WHERE room_spend.spent + $kobo <= limit RETURNING`), reserved BEFORE the charge starts and released (`releaseSpend`) on failed, reversed or never-paid sprays. Daily limit: serialised per payer by `pg_advisory_xact_lock(hashtext('spray-daily:'||payerId))` then a sum over `spray_payments` in status `created,pending,paid,delivered,reversing,disputed` in the last 24 hours (rolling, not calendar) plus the new price. Raising a limit above the default needs `isIdVerifiedAdult`. A limit is read from the database each time, never from the client. Velocity: 10 per minute and 60 per hour per payer, plus 3 per minute per (payer, recipient), enforced with a database-backed count (works across processes), on top of a normal per-IP limiter on the route.
6. **Exactly one charge, exactly one delivery.** Per-reference serialisation: in-process `keyedQueue.ts` plus `pg_advisory_xact_lock` on the reference hash inside `finalizeSpray`, and conditional UPDATEs (`WHERE status = 'paid'` to `delivered`). Delivery and its ledger row commit together (`recordTransaction(tx, { tx })` throws on failure, like phase 4). The broadcast happens AFTER commit and is never the source of truth; a broadcast failure never undoes a delivered spray.
7. **Reverse, never strand.** Paid but undeliverable (recipient left, lost stage, banned, unverified, room ended, host changed, over the new-host receive cap) = full refund through the provider, status `reversing` until the provider says processed, then `reversed`; payer told plainly (chat line to the payer only, plus the response/notification). The sweep job runs every 15 seconds: delivers anything `paid` and still deliverable, reverses anything `paid` older than `DELIVERY_DEADLINE_MS` (60 s) after payment was detected, re-verifies `created` / `pending` older than 10 minutes with the provider (paid means finalize, not paid means `failed` and release the reserved spend), and completes `reversing` refunds. It is safe to run on every process at once (advisory lock plus conditional UPDATE).
8. **Saved cards.** Only saved when the payer sends `saveCard: true` (an explicit checkbox, default off) AND the provider says `reusable`. Authorization code is encrypted with AES-256-GCM (`PAYMENT_TOKEN_KEY`, 32 bytes base64, key id prefix `v1:`), never logged, never returned, never in any API response, never in the webhook log. `unique (user_id, signature)` prevents duplicate cards. The key is required only when the `spray` flag is ON or a card is being stored: in production with the flag ON and no key the process refuses to start; with the flag OFF encrypt/decrypt just throw if ever called (**do not make a production boot fail while the flag is off**, the key is not set yet). `DELETE /api/users/me/spray/method` soft-deletes and wipes `auth_enc` (set to empty string, set `deleted_at`).
9. **3D Secure at 10,000 naira and above** (`bag`, `rain`): never charge a saved card silently; the provider returns `action_required` with an authorization URL, or the endpoint starts a first-payment style checkout. `note` and `bundle` may use a saved reusable card.
10. **Chargebacks and clawbacks.** A dispute on a spray reference: conditional UPDATE to `disputed`, ledger `chargeback`, `host_clawbacks` rows (host share, and the guest share when a stage guest), idempotent per (spray, beneficiary) via a unique index, nothing deleted. `applyClawbacks(hostId, availableKobo)` is called by settlement inside the payout computation; clawbacks are `written_off` only by an admin (audited with a reason).
11. **New host receive cap** (config `NEW_HOST_RECEIVE_CAP_KOBO`, default 5,000,000 kobo, first 14 days after the host account's first spray eligibility or account creation, whichever the existing data supports; document the choice): enforced at start and again at finalize; over-cap means refuse at start with the generic 403 and reverse at finalize.
12. **Webhook safety.** Same rules as tickets: raw body, HMAC signature check (the fixed constant-time compare in `server/payments/paystack.ts`), provider re-verify before trusting an amount, `meta.type === "spray"` branch only after the reference MAC passes. A malformed or string metadata body must not fall through silently: if `looksLikeSprayReference(reference)` it is a spray charge and a transient problem answers 500 so Paystack retries.
13. **Hub safety.** The `room:spray` event carries `{ type, id, tier, v3c, fromId, toId, at }` only: ids are the payer's and recipient's user ids exactly as members appear in `room:state`; never an amount in kobo beyond what `tier` implies, never a card, never a reference. The receipt chat line is a server-made normal chat line (`system` style as the existing code does) so the client never invents one.
14. **Abuse.** A payer cannot spray themselves (`SELF`, generic 403), cannot spray a person who blocked them or whom they blocked (generic 403), cannot spray while a previous spray of theirs to the same recipient is `created`/`pending` for under 10 seconds with a different key (one in flight per payer and recipient), and a room with 0 other members is not spray-eligible.
