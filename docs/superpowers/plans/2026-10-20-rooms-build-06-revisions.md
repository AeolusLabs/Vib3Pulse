## A. Rules (hard)

1. **NO TESTING.** Write code and NEW test files (`scripts/test-rooms-{unit,api,ws}-<topic>.ts`), run nothing: no tests, tsc, build, browser, dev server, DB script, install. Act as the compiler (10 baseline tsc errors exist, add none). Say "nothing was run". Never dispatch subagents. Never touch `.env` or the database; the orchestrator applies migrations after reading them.
2. **Anonymous join is scrapped.** Ignore every mention (recap, notifications, runbook: no `ROOM_ANON_SECRET`, no `ROOMS_ANONYMOUS_JOIN`). Flags: `paidRooms` (`ROOMS_PAID`), `spray` (`ROOMS_SPRAY`), `linkScreens`; all OFF. Never switch a flag on, never push.
3. **Money visibility.** No screen or API shows another person's earnings, payments or identity. All amounts come from stored rows (integer kobo), never recomputed from client input. A host sees a payer's identity nowhere (ticket and spray rows carry no payer for hosts). Bank account numbers are never returned in full: last four only, and the resolved account NAME from the bank lookup is never returned either (only a boolean `nameMatches`).
4. Sensitive fields only through the shared sanitizers plus the global redaction; never `req.login()` / `req.session.regenerate()`. Never log account numbers, authorization codes, BVN/NIN or emails.
5. Copy: plain words, no em dashes, never the word "cash", no "anonymous". Violet is the one accent, AMBER only for money moments (earnings, receipts, price chips) with a 4.5:1 contrast check, destructive token for warnings. Icons only from `@/components/ui/icons`. 44 px targets, labels, focus return, reduced motion.
6. Schema changes additive and idempotent: SQL file in `migrations/` + `ensureSchema` batch in `server/storage.ts` (via a small `server/rooms/<name>Migration.ts`, copy `sprayMigration.ts`) + Drizzle in `shared/schema.ts` + runner `scripts/run-<name>-migration.mjs`. Not applied by you.
7. Settlement language: a host is told "settled" ONLY when Paystack reported it (payout row `paid` with a verified transfer, or a settlement the provider confirmed); otherwise "on its way". Never "paid" from an estimate.

## B. Per task decisions

- **6.1 payout account.** One helper `hostPayoutReady(userId)` (new, in `server/rooms/payouts.ts`) is the single source for "has a verified payout account"; make `canSellTickets`'s server input and the spray eligibility input read it (find where phase 4 and 5 compute `hasPayoutAccount` / host payout and route them through the helper; keep behaviour identical). The account-resolve endpoint is a lookup oracle on third parties' bank details: require signed in + `isIdVerifiedAdult` + strict per-user rate limit (5 per hour) + per-IP limit, never return the resolved name, only `nameMatches`. Name match is normalised (case, spacing, order, diacritics) against the user's verified legal name field the repo already stores; if none exists refuse with `NO_VERIFIED_NAME` and list that as an owner item. Creating the subaccount is idempotent (second call updates). Changing the account while a payout is `queued` or `held` is allowed but must not redirect an in-flight transfer: the payout row snapshots the recipient at queue time (check phase 4 settlement; if it re-reads the account at transfer time, snapshot it or block the change while a payout is queued, and say which). An audit log line for every account change.
- **6.2 earnings.** `computeEarnings(rows)` pure + tested with a generated-history property test (deterministic seeded generator, no new dependency). Inputs are the stored rows: delivered `spray_payments` host/guest shares (the user as host_id gets `host_kobo`, as recipient with a guest share gets `guest_kobo`), paid `room_tickets.host_kobo`, `room_payouts`, `host_clawbacks` (open amount minus recovered), refunded/reversed rows subtract. "Settled" per revision A7. Spray shares of a payer's refunded/reversed spray are not earnings. Ranges by `created_at`/`delivered_at` in UTC. `byRoom` shows only rooms where the viewer is host or paid guest recipient. A user who lost verification keeps history (read works) but is not eligible to receive (phase 5 gate already does that; do not change it).
- **6.3 receipts.** Own rows only (payer = viewer): ticket rows, spray rows, refund rows (negative). Pagination by `(created_at, id)` cursor, stable. The HTML receipt is generated server-side with every interpolated value HTML-escaped, `Content-Type: text/html; charset=utf-8`, `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`; contains tier/ticket name, room title, amount, VAT, payment date, masked card last4 if stored, receipt number derived from the id; never a recipient's or host's personal details (room title only); business details from config placeholders.
- **6.4 notifications.** Add types `room_ticket`, `room_refund`, `spray_received`, `payout_paid` if not present (check `notificationTypes`, `spray_reversed` exists from phase 5). `notifySprayReceived(recipientId, roomId, kobo)` batches per (recipient, room) into ONE notification updated at most once a minute, multi-process safe (a conditional UPDATE/UPSERT keyed on an unread notification for that recipient+room, not in-process memory alone; injected clock for tests); the copy never names the payer. A host receiving 300 sprays in a minute gets one notification (plus at most one update per minute). Hook the real events (ticket issued, refund issued, payout paid, spray delivered) with small local edits; every hook is fire-and-forget (a notification failure never fails a money path). Links: `/rooms/:id`, `/rooms/earnings`. Update the client `NotificationBell` mapping (copy + link per type, plus icon from the shared icons).
- **6.5 recaps.** `GET /api/rooms/:id/recap`: 404 for anyone who was never a member (use the persisted membership/attendance data phase 1-4 keep; if none exists for a room, add the smallest additive record or table, say so in the report and the migration), 404 for rooms not ended, host-only fields only to the host (`hostRoom` sanitizer style), never others' identities beyond what the room already showed. Track `peak` in `RoomHub` and persist `rooms.peak_members integer` on end (additive column, migration `add_room_peak.sql`). `followersGained` = follows of the host created during the live window by room members (or omit the field and say so if the data is not trustworthy; never guess). `earnedKobo` for the host only, from stored rows.
